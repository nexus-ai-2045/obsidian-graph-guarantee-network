# 第二脳・メモリー・Obsidianの統合設計

状態: 提案。既存repoへ責務を統合する設計であり、実装・導入・同期の完了を示さない。

## 統合先と正本

本repoを、ノート接続保証と第二脳の共通契約・検証条件の統合先とする。既存の記憶・同期・スキル等の実装は各所有repoに保持し、一括移管しない。新しい第二脳repoは作らない。既存の `tools/` とコマンドの互換性を保持し、必要な追加は既存機能・外部OSSを再利用する。

共通機構の設計は本書、個人環境への適用計画は各利用者の管理領域を正本とする。利用者の知識本文、原資料、承認履歴、runtimeメモリー、認証情報、端末の絶対パスは本repoへ収容しない。複数repoを一つの保管庫にするのではなく、一つの対象について正本と更新者を一意に解決できる状態を目指す。

| 対象 | 正本・更新責務 | 派生と接続 |
|---|---|---|
| 接続保証コード・共通契約・検証条件 | 本repo。既存の他機能コードは各所有repo | 各端末のcheckoutは配布された版 |
| 人が使う知識・Wiki | 利用者の既存Markdown分類 | Obsidianは閲覧・編集の入口。別のWiki本文を複製しない |
| 原資料 | 利用者の既存source store | 出典ID・版で知識から参照 |
| AI固有のメモリー | 各runtimeの所有領域と更新権限 | 共通知識への参照を使い、無許可で同期・上書きしない |
| 意味検索・Graphitiの索引 | 原文から再生成する端末別派生物 | source ID・版・生成方式を保持 |
| 端末対応・配送設定 | 利用者の既存台帳・同期runner | 本repoは契約と検証結果を提供。別の台帳・runnerを新設しない |

## 既存機能の配置

- Wiki化: 原資料、知識、規約を分離する既存のWiki化方針と分類を再利用する。抽出は候補、正式採用は人。Ingest / Query / Lint / Logを既存処理へ対応付ける。
- 操作: 既存の `obsidian-cli` と `obsidian-markdown` スキルを利用する。スキル本文を本repoへコピーしない。CLIは対象Vaultと正確なpathを指定し、未起動・対象不一致で書込みを止める。
- 接続保証: 現在のupdater / audit / test / verifyを維持する。「本文を編集しない」は接続保証モジュールの不変条件である。将来の承認付き知識編集は別の明示操作とし、updaterへ混ぜない。
- 検索: 利用者が採用済みの検索を既定にする。Graphitiは追加候補であり、導入しなくても基本の知識管理・同期が成立する。

## Graphitiの役割

[Graphiti](https://github.com/getzep/graphiti) は、対象・関係・事実の変化を時系列で保持し、出典へ戻れるグラフを構築・検索するOSSである。たとえば「案件の現在の担当」と「以前の担当」を区別する検索に使う。Obsidianの表示グラフやファイル同期の実装ではない。

導入する場合も原文を正本とし、抽出された関係の正しさを自動的に保証済みにしない。モデル・DB・運用経路が必要であり、利用者の許可済みwrapperと実行設定を使う。必須化と既定検索への昇格は、採用判断と比較検証を経て別に決める。

## 整合性を保証する契約

| 原則 | 不変条件 | 検知と修復 | 必要な証拠 |
|---|---|---|---|
| 正本一意 | source IDから正本・owner・版に一意到達 | 複数・欠落・循環を検知し、既存台帳のownerへ差戻し | 対象範囲の照合結果 |
| 明示採用 | AI正式反映は候補ID・target・base hash・proposed hashに承認が結合 | 内容・基底変更で承認を失効し再判断 | 本文readbackと承認参照 |
| 二重更新防止 | 同一対象のwriterを排他し、反映と記録の中断を回復可能にする | キュー移行時は両writer停止・保全・照合。衝突時は再開しない | 中断・再実行で消失と二重反映0件 |
| 時間分離 | 現在・過去・不明を区別 | currentとas_of併用拒否。出典版欠落はhistory_incomplete | 訂正・撤回・遅延取込みの固定試験 |
| 生成物分離 | 接続用の生成リンクを知識の関係として取り込まない | 実設定の生成先・生成元で取込み除外。人の正当なリンクを保持 | 生成先変更後も検索・候補・Graphitiに混入0件 |
| 同期証明 | 内容・適用版・索引版・端末の観測を区別 | offline / conflict / unknown / index_pendingを表示し、復旧後に再試行 | MacとWindowsの対象版readback |
| 再生成可能 | DB・索引は正本と固定した生成方式から復元 | 版欠落・抽出失敗を明示し、不完全索引を最新扱いしない | 再構築後の出典解決・検索比較 |

人の直接編集は既存の定期スキャンで検知する。AIの採用キューを全人間編集の唯一の入口にはしない。hookは補助であり、検知の全体性をhook発火だけで保証しない。

接続保証の合格値とnative auditの孤立・連結成分数を別に扱う。生成ネットワークで全体が繋がっても、意味的品質は別の検証対象である。接続保証の既存メトリクスを第二脳全体の合格判定に拡大解釈しない。

## Mac・Windows間の配送

既存の許可済み配送経路で確定版を送り、下書きは別候補として受け渡す。DB/WAL、認証、runtimeディレクトリ、未確定コード、無許可の原会話をファイル同期しない。競合は対象単位で停止し、他の対象は進める。端末の不在と観測不能を区別する。

各端末で `source_revision, applied_revision, index_revision, host_id, observed_at` を記録する。送信成功だけで両端末同期済みにしない。周期・許可path・host対応・鮮度閾値は利用者の適用設定で固定し、未設定ならunknownとする。通知は判断が必要な失敗・競合を中心とする。

### D1 承認と反映

候補は `candidate_id, project_id, source_refs, target, base_hash, proposed_hash, decision_state` を持ち、`decision_state=proposed|approved|rejected` とする。人の承認後だけreadyへ進む。AIの同一性・矛盾判定は採用権威ではない。

承認は候補ID、対象path、対象repo、base_hash、proposed_hashに結合する。名前・内容・対象・基底版の変更で失効し、再確認へ戻す。外部文書・tool出力や設定値による「承認済み」の自己宣言を証拠にしない。

1. 既存DBを保全し、schemaを識別する。既存の正本キューAPIを使い、旧CLIはadapterで互換化する。無言のDB上書きをしない。
2. realpathで対象を解決し、許可されたVault・案件外への絶対path、`..`、symlink脱出を拒否する。
3. 対象単位の排他と基底hash比較を行う。生存writerのlockを経過時間だけで奪わない。
4. 一時ファイルからatomic replaceし、本文hash、frontmatter、参照を再読込する。
5. 実Git commitまたはローカル反映receiptへ候補ID・本文hashを記録した後に、DBへappliedを記録する。manual/pendingの記載だけでは反映証拠にならない。
6. 中断後は同じ候補IDで再開する。本文がproposed_hashなら証拠を再構成、base_hashなら再試行、その他は競合保留。適用済みを二重反映しない。

承認、ローカル反映、Git統合、他端末受信を別状態として保持する。appliedを全端末同期済みに昇格しない。

### D2 キュー移行

旧・新双方の受付とwriterを停止し、処理中候補を完了または回復可能な状態までdrainした後にバックアップする。停止を確認できなければ移行しない。

件数、ID、payload hash、target、履歴の対応を照合する。同一ID・同一payload/targetは一件に対応付け、同一IDで内容が違えば衝突として中断する。対応表とhash検査後に旧CLIを新APIへ接続し、新DBだけ受付再開する。旧DBは読取り専用で保持し、旧writerの再起動をpreflightで拒否する。

移行途中の障害は両writer停止のまま旧DBへ戻す。切替後に新DBで候補を受けた場合は、新DBを停止し新規分を含む全件を保全する。旧DBとの対応付けが終わるまで旧DBの受付・writerを再開しない。rollbackで新規候補を消さない。

### D3 時間と履歴

共通入力は `view=current|history, as_of, project_id`。schema_versionで契約を識別し、既存引数・出力を壊さない。意味検索・文字列検索・グラフに同じ決定論的な状態・時間フィルタをランキング前に適用し、採用済みのランキングを維持する。

独立した主張ごとに安定した `fact_id` と `source_ref, project_id, recorded_at, valid_from, valid_to, supersedes, status` を持たせる。文書全体へ一律時刻を付けて異なる主張を混ぜない。文書単位IDから段階移行できるが、根拠のない時刻はunknownとする。

- recorded_atは記録の確定時刻、有効期間は `[valid_from, valid_to)`。timezoneを必須とし内部UTCで扱う。mtimeやGit commit時刻から事実の有効時刻を補完しない。
- currentは正本・採用状態・明示的後継を確認し、失効済みを現在根拠から除外する。時刻不明はunknown枠に分け、最新と断定しない。
- historyは旧版と後継関係を返す。as_ofは事実の有効時刻だけを意味し、当時の知識時点検索は本版の対象外とする。時間根拠不足は回答不能とする。
- as_ofはhistoryだけに許す。currentとの併用はvalidation errorであり、無言の切替をしない。過去の選別は有効期間で行い、現在supersededという理由だけで除外しない。
- 有効期間の矛盾はconflictとする。取込みが新しいだけで旧事実を無効にしない。
- 結果は `fact_id, source_path, source_revision, source_hash, source_location, temporal_status, index_revision, sync_state, backend, warnings` を含み、返す前に正本へ再照合する。古い索引は再生成待ちとする。
- 意味検索停止時は文字列検索へ縮退できるがbackendと理由を表示する。時点検索を再現できない時に現在情報を代わりに返さない。

履歴は承認済みGit commitの本文から再構築する。知識単位の最初の取込みcommitを起点に、変更commitとblob hashをrevision manifestへ列挙する。上書き・改名・削除後も固定commitからfact_id、旧path、有効期間を復元する。未承認branch・未commit本文をhistoryへ混ぜない。

必要commitの到達可能性を保ち、履歴書換え・prune前に所有担当による保全検査を要求する。必要版が取得できなければhistory_incompleteとして該当期間の断定を止める。Graphiti episodeを含む全backendは同じ承認済みrevision manifestから再生成する。

### D4 Graphitiの接続と回復

Graphitiの必須化は未決であり、基本工程を止めない。採用時はOSSを再利用し、Graphiti・DB・モデル・schemaの版をlockfileとmanifestに固定する。更新時は同じ評価セットで再検証する。DBは端末別の派生物でありファイル同期しない。

LLM・埋め込みは許可済みwrapper経由のadapterを使う。SDK既定のcloud clientを暗黙生成せず、外部LLMへの自動fallbackをしない。利用可能なwrapperがなければ接続工程を停止しruntime担当へ返す。model profileは構造化出力試験を通してから取込みに使う。telemetryと無許可の外部通信を無効化し、接続検査で確認する。

同期済み・承認済みMarkdownだけをepisodeへ投影し、raw会話、未承認候補、認証、生成接続用ノードを除外する。episodeは出典・hash付きの派生コピーである。正本ID・source hash・schema versionでキーを冪等に生成し、groupを案件ID、writerをローカルgraphごとに一つにする。別案件の同名entityを無条件統合しない。

推定された失効・関係を正本の明示情報へ照合する。推定でMarkdownを更新せず、照合不能な関係はcandidateとして現在回答から除外する。

確定commit差分の取込み完了後にsource revisionとmanifestを更新する。manifest更新前の中断は同じキーで再送する。削除・撤回は正本tombstoneへ追従し、撤回済み本文を結果へ出さない。

再構築は別generationで行い、件数・出典hash・時間検索を検査後に切り替える。旧generationはrollback用に保持する。非決定的なLLM出力のbyte一致を要求せず、出典集合・明示fact・評価ケースで同値性を判定する。

障害時は既存検索を利用できるが、指定された時間・関係検索を代替できなければunavailableを返す。縮退成功をGraphiti合格に数えない。G1実backendと出典readback、G2両OSの訂正・分離・再構築、G3同一評価セットによる比較を実装完了の条件とする。既定化は別判断とし、必須採用後の未完了を環境不足で勝手に対象外にしない。

### D5 配送

自動配送の入力は `repo_id, remote, branch, host_id, allowed_paths, approved_revision, permission_ref` に結合する。未承認・不明ならread-only。permission_refは実際に得た許可への参照であり、任意設定による自己承認を認めない。候補作成と外部配送は別権限である。

確定版は既存のPR/merge gateを通った承認済みcommitを配送する。受信先はcleanな対象checkoutだけfast-forwardし、dirty・競合なら作業を保持する。下書きは許可済み文書pathのみ端末別候補branchへ保存し、相手は別worktreeで参照する。作業中ファイルへ直接上書きしない。

既存runnerへ確定後wakeと定期確認を接続する。hookでLLMを呼ばず、索引更新はworkerへ渡す。runner未接続は接続前の状態として記録し、稼働済みに数えない。送信側・受信側それぞれが対象版・適用版・索引版・host・観測時刻を記録する。受信証拠は既存の許可済み経路で本文を含めず共有する。

周期、receiptの鮮度上限、許容時計ずれ、再送間隔・上限を適用設定で固定する。未設定はunknownで自動更新しない。古いreceipt、許容超の時計ずれ、送信成功だけではsyncedとしない。

| 状態 | 条件と動作 |
|---|---|
| synced | 対象版を両端末が適用済み、未送信変更なし、新鮮なreadbackあり。索引版が違えば検索はindex_pending |
| pending | 送信・受信・適用待ち。次周期で再試行 |
| offline | 接続失敗。下書きを保持し同期済み表示を外す |
| conflict | 履歴分岐・dirty・同一候補不一致。対象だけ保留し他案件は継続 |
| unknown | host・remote・許可・receipt不明、時計ずれ超過、必要設定欠落。自動更新しない |

候補IDとrevisionで再送を冪等化し、設定した上限まで間隔を広げ、復旧直後に再確認する。通常の不変状態は通知せず、人の判断が必要な競合・復旧失敗を通知する。

Git管理外は既存のscope契約に従う。Vault全体、Git内部、DB/WAL、runtime領域、認証をファイル同期しない。未commitコードの共同編集・raw会話・AI固有メモリーのコピーは本配送の対象外。OS別のpathとhostを実測台帳で解決し、一方の不在から他方の不在を推定しない。

### D6 観測

調査rootと最大深さを適用設定で固定し、その範囲の隠しフォルダも観測する。登録先は深さにかかわらず個別statする。依存・cache・Git内部・runtime secretへ降りず、symlinkは参照先を記録するだけで再帰追跡しない。フォルダ棚卸しに本文・総容量・全件ファイル数の走査を混ぜない。

最小schemaは `host_id, observed_at, path, project_id, role, canonical_ref, evidence, coverage, finding`。roleは正本候補/作業コピー/派生/外部参照/保管/未分類。正本候補という観測と正本宣言を区別する。

findingは未登録・欠落・範囲外・別host専用・未確認・一致を分ける。権限拒否や観測不能は欠落としない。未登録だけで削除対象にせず、同名・小容量だけで重複認定しない。移行前にcase衝突、OSの名前制約、symlink差異を検査する。既存列挙器の深さ制限モードを再利用し、案件固有の分類規則を調査root全体へ流用しない。結果は派生報告、台帳更新はownerへ差分で渡す。

### D7 Wikiと操作

既存の分類・Wiki化方針・skillを参照し、別のWikiフォルダや採用経路を作らない。Wiki候補からSchema・runtimeメモリーを自動昇格・変更しない。原資料、一回限りの出来事、永続規則を区別し、それぞれの所有・採用ゲートを守る。

CLIは対象Vaultと正確なpathを明示し、直近フォーカスのVaultや曖昧basenameへ依存しない。未起動・利用不可・対象不一致なら書込みを止め、既存の読取り経路で照合する。別Vaultや無承認の直接反映へ切り替えない。

生成専用フォルダとノード・エッジを意味検索、Wiki候補、Graphitiの共通前処理で除外する。除外元は実設定・生成元・対象pathで記録し、名前の部分一致だけで人のノートを除外しない。生成先変更にも追従する。生成物を除いたnative auditを別に保持し、曖昧・欠落リンクを辺にしない。監査集計は運用証拠として参照できる。

### D9 期待動作レビューによる追加条件

#### 人の同時編集と確定までの経路

D1のlockは、同じlockを守らないObsidian・外部editorの書込みを防がない。atomic replaceも基底比較との間の競合や、editorの未保存bufferによる後の上書きを防がない。AIは自分が排他所有する作業コピーへ候補を反映する。人が編集できる実ファイルへの自動反映は、全writer・editor bufferを含む安全な受渡しを実証できる場合だけ許す。実証できない場合は候補と差分を保持し、人の反映へ戻す。単なる直前hash再検査を排他の証明にしない。

人がObsidianで書いた内容は定期スキャンで未確定変更として検知し、差分・出典・対象版を示す。人による保存自体を、外部配送・別repo反映・Schema変更の許可へ拡張しない。既存の採用・commit/merge経路で確定版を作る。AIのローカルappliedからも同じ経路へ進み、統合済みrevisionが得られるまでは配送待ちとする。図の「反映→正本」にはこの確定工程が含まれ、保存だけで承認済みGit履歴が生まれるわけではない。

#### Gitの配送範囲と競合解消

allowed_pathsはGit transport自体をpath単位に制限しない。候補branchにも祖先commitが含まれるため、送るrefから到達する履歴・blobと配送先の閲覧権限を確認する。repo全履歴の配送が許可された相手には既存Git経路を使う。許可が一部pathだけなら、承認済みの独立した配送履歴・export方式が既にある場合だけ使い、元repoのbranchをそのままpushしない。未整備なら配送を止め、別経路を無許可で新設しない。

dirtyによる保留は実checkout単位である。同一checkout内の他案件まで動かせると保証しない。「他案件は継続」は既存の独立checkout・worktreeに隔離されている対象だけに適用する。人の作業checkoutを自動stash・resetしてcleanにしない。競合は共通基底・双方の差分を保持してownerへ渡し、採用された解消版へ承認を結び直す。その版の統合後に配送を再開する。

#### 回答に使える版

内容のsyncedと索引の準備完了は別である。回答時は対象repo・案件・revision manifestを固定し、取得結果のsource_revisionとindex_revisionを照合する。端末がofflineまたは相手側未観測なら「ローカル確定版時点」と表示し、全体の最新を断定しない。準備前に古い索引を無言で使わず、同じ確定版から読取り可能な縮退結果を返すか、準備待ちを返す。

AI固有メモリーに旧情報があっても、現在の事実の権威にしない。更新される事実の回答では共通正本の版を確認し、古いメモリーとの不一致を記録する。メモリーの書換え権限がなくても古い事実を現在回答から除外できることを各runtimeで試す。正本へアクセスできなければ鮮度不明とする。

保持情報にもsource ID・revisionを結び、利用時に版と撤回状態を確認する。確認できない保持情報は現在根拠に採用しない。検索を呼ばず保持情報だけで答える経路も対象とし、継続turnと再開sessionの両方で試す。

#### 訂正・撤回・抜粋の共通選別

fact_idは論理的な主張、fact_version_idはその版を識別する。回答の基準revision manifestで承認された訂正関係を先に解決し、その後に有効期間を評価する。「1月はA」と後日記録された「1月はBだった」という遡及訂正は、承認済みの訂正関係がある場合にBを回答根拠とする。旧A版は来歴として保持する。訂正関係がない独立した主張の衝突はconflictのままであり、取込み順では選ばない。

通常の失効、ファイルの改名・削除、回答根拠からの撤回を区別する。失効は有効期間に従って過去検索に使える。ファイル削除だけから失効・撤回を推定しない。撤回は対象ID・版・適用範囲を承認済み正本へ記録し、意味・文字列・Graphitiのcurrent/history双方で返却直前に除外する。raw履歴の保全は回答利用の許可を意味しない。

索引再構築・generation rollbackでも現在の承認済み撤回判定を古い版に戻さない。撤回判定の鮮度を確認できなければ未確認とし、撤回なしを推定して返さない。これは知識時点検索の追加ではなく、現在の利用禁止を全回答へ適用する条件である。

chunkとfact_version_id・本文範囲の対応を保持する。ランキング前の適格性判定に加えて、回答用抜粋・要約・runtimeへ渡す本文も適格な主張の範囲に限定する。有効な一文と失効・撤回された一文が同じchunkにある場合、chunk全文を渡さない。分離不能ならそのchunkを現在根拠にせず、情報不足を表示する。出典位置への参照は保つが、除外本文を回答用contextへ混ぜない。
